# C++ 语言实战（十二）：跨平台交付——交叉编译与静态链接

性能这条线到上一章全部收口，但网关的最后一公里还没走：代码要在客户形形色色的机器上活下来——ARM 边缘盒子、客户自带的 x86 工控机、十年没升级的老 CentOS。这一章的事故是工业软件的入门税，每个团队都交过一次：「在我机器上编译好好的，拷到客户机器启动就崩。」顺带把 ch10 埋的工具链纪律正面拆解——静态链接不是「拷贝即用」的万能钥匙，用错了地方就是 RTTI 失配的复发。

## 一、事故现场：GLIBC_2.29 not found

新版本网关首次交付到客户的老工控机（CentOS 7.9），启动第一秒就死：

```text
./blog-gateway: /lib64/libc.so.6: version `GLIBC_2.29' not found
(required by ./blog-gateway)
```

开发机是 Ubuntu 24.04（glibc 2.39），二进制在开发机上跑得干干净净——「在我机器上是好的」这句话的字面意思没有错，错的是这句话本身没有信息量。祸根在编译环节：开发机上的 glibc 2.39 悄悄把一批符号打上了新版本标签，二进制从此带上了「需要 glibc ≥ 2.29」的隐性依赖，而 CentOS 7 的 glibc 停在 2.17。**glibc 的兼容性是单向的：新系统跑老二进制没问题，老系统跑新二进制，一步都走不动。**

复核 ch10 事故后的插件交付纪律时又抓到一处隐患：某个内部工具 .so 是同事在另一台老 Ubuntu 16.04 上编的，链接的还是旧 libstdc++——虽然逃过了 RTTI 失配，但「插件工具链五花八门」这个状态本身就是下次事故的温床。兼容性问题从来不是单点，是**交付矩阵对不上构建矩阵**的系统性失配：客户环境有 5 种（x64 CentOS 7 / x64 Ubuntu 20 / ARM64 Debian 10 / ARM64 OpenEuler / Docker 镜像），构建环境只有 1 种（开发机）。

## 二、排查过程：让二进制交代自己的出身

第一步，确认依赖落差。`ldd --version` 对比两端（2.39 vs 2.17），`ldd blog-gateway` 列出全部动态依赖。第二步，追问「到底是哪些符号要 2.29」——`objdump -T blog-gateway | grep GLIBC_2.2[2-9]` 一眼定位：`std::filesystem` 相关路径调用的 `stat` 等符号绑定了新版本标签。第三步，审计整个交付物的工具链构成：主程序（Ubuntu 24 gcc 13）、两个内部 .so（各自不同环境编的）、客户插件（自带静态运行时，ch10 的老案底）——**一个部署包里藏着四套出身**。排查的结论因此从「修这一个包」升级为「修交付体系」，这是本章最重要的定性。

## 三、底层原理：符号版本、交叉编译与链接的三种姿势

### glibc 符号版本：兼容性单向阀

glibc 对外符号带版本标签（`GLIBC_2.17`、`GLIBC_2.29`……），同一个函数名可以同时存在多个版本实现。编译时，链接器把你**实际引用的每个符号的最高版本**记进二进制；运行时加载器逐项核对目标 glibc 是否提供。于是「编译机的 glibc 版本」就是二进制的隐性最低系统要求——这就是构建环境决定兼容下限的机制根源。同名符号多版本共存的设计让 glibc 保持了传奇级的向后兼容，但它保护的是「老二进制跑新系统」，没人能保护「新二进制跑老系统」。

### 交叉编译：编什么，就用什么的头文件和库

交叉编译 = 在 A 平台生成 B 平台的二进制。三个关键词：**工具链**（`aarch64-linux-gnu-gcc`，三元组「架构-系统-库约定」点名目标）、**sysroot**（「目标系统的根目录」副本，编译器从这里找目标平台的头文件与库——用目标系统的 glibc 头文件编译，自然不会引入本机的新符号）、**CMake 工具链文件**（把工具链和 sysroot 声明成一份配置）：

```cmake
# aarch64-toolchain.cmake
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)
set(CMAKE_C_COMPILER   aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)
set(CMAKE_SYSROOT /opt/sysroot-debian10-arm64)   # 目标系统的根
```

sysroot 是交叉编译的灵魂，也是最容易敷衍的地方——sysroot 里目标系统的 glibc 老不老，直接决定产物的兼容下限，和第三节的构建镜像原则同源。

静态与动态的选择必须叠加 ch10 的教训一起做：**多 .so 架构里，运行时库必须全进程统一**——要么统一动态（一份 libstdc++ 服务所有模块），要么由主程序静态持有并导出符号、插件绝不能各自打包运行时。ch10 的 RTTI 失配，本质就是「静态链接」这个词被每个模块独立行使的结果。

## 四、正确姿势：构建矩阵对齐交付矩阵

修复的主轴一句话：**让每一种客户环境，都有对应的容器化构建环境**。

```yaml
# CI 矩阵：目标环境 ↔ 构建镜像一一对应
matrix:
  - { os: centos7-x64,   image: centos7-gcc9-x64 }      # 编出来的符号最高 2.17
  - { os: ubuntu20-x64,  image: ubuntu20-gcc9-x64 }
  - { os: debian10-arm64, image: debian10-gcc8-arm64, toolchain: aarch64-toolchain.cmake }
  - { os: openeuler-arm64, image: openeuler-gcc9-arm64 }
# 链接策略统一：-static-libstdc++ -static-libgcc，glibc 动态
```

原则就一条：**用最老的目标系统做构建环境**——在 CentOS 7 容器里编译，符号版本上限天然锁在 2.17，产物向上兼容全部更新系统。插件与主程序全部出自同一批构建镜像（ch10 的纪律正式落地为 CI 配置），四套出身的乱象就此绝迹。产物命名带全三件套（`gw-2.3.1-debian10-arm64.tar.gz`），启动自检打印构建信息（代码版本 + 工具链版本 + 目标平台），客户现场第一时间的报障截图就能对上号。再加一道保险丝：启动时读 `/lib64/libc.so.6` 的版本与依赖清单核对，不满足就打印人类可读的错误退出——**宁可死得明白，不可死得沉默**。

包体账也报一下：主程序动态链接 31MB（依赖另算），半静态后 33MB（多吃两份静态库），musl 全静态 19MB 单文件——体积从来不是选静态的理由，**依赖的确定性才是**；反过来，一旦插件化架构在身，运行时统一是比「单文件」重要得多的目标，我们的最终选择是半静态 + 构建矩阵。

## 六、面试怎么答

**Q1：什么是交叉编译？怎么搭建？**
定义 + 三件套：工具链（三元组命名目标平台）、sysroot（目标系统根，决定头文件与库的版本下限）、CMake 工具链文件（配置固化进版本管理）。加分项：讲 sysroot 的新旧决定产物兼容下限——sysroot 里是老 glibc，产物就不带新符号；这是用「构建环境锁死兼容性」的思路。

**Q2：静态链接和动态链接怎么选？**
按维度答：部署确定性（静态赢）、体积与内存（动态多进程共享赢）、安全更新（动态 patch 一次全升级赢）、插件机制（必须动态或主程序统一持有运行时）。glibc 全静态的 NSS/dlopen 陷阱主动讲，musl 作为真静态的替代路径。工业结论：单文件工具选 musl 全静态，多 .so 系统选半静态 + 统一构建镜像——能把 ch10 RTTI 失配的案底讲出来直接封顶。

**Q3：「在我机器上是好的」怎么系统性解决？**
这是工程流程题不是技术题，按体系答：交付矩阵 ↔ 构建矩阵一一对应（容器化最老目标环境）；产物带平台标签与构建信息；启动自检 + 人类可读报错；CI 里加「产物 smoke test 跑在目标环境容器」环节。收尾一句：这句话的正确翻译是「我们的构建体系覆盖不了你的机器」。

**Q4：为什么新编译的程序在老 Linux 上报 GLIBC 版本错误？**
符号版本机制：编译时绑定引用符号的最高版本标签，运行时加载器核对目标 glibc。glibc 只向后兼容（老二进制跑新系统），构建环境的 glibc 就是产物兼容下限。解法按强度：老环境容器内构建 / 交叉编译配老 sysroot / 静态化绕开（注意 NSS 陷阱）。

## 七、落地清单

- 交付矩阵明文维护，每种客户环境对应一个 CI 构建镜像，用最老目标做构建环境
- 全项目统一半静态（-static-libstdc++ -static-libgcc）；多 .so 架构下运行时库必须进程级统一
- 交叉编译必配 sysroot，工具链文件进版本管理，禁止「本机顺手编一个」
- 产物命名带版本-平台-工具链三件套，启动自检打印同款信息并核对 glibc
- 不满足依赖时人类可读报错退出，宁可死得明白
- CI 末尾加目标环境容器 smoke test，兼容性问题在合并前暴露
- 新增第三方依赖先问一句：它引入了什么 glibc/符号版本下限
