# C++ 语言实战（四）：虚函数与插件化协议驱动——三种协议热插拔

前三章的网关只认 Modbus，日子过得简单。变故来自销售部门的一句转述：「客户 B 的设备只讲 OPC UA，客户 C 的老旧涂布机是厂里私有 TCP 协议，都得接。」这不是功能问题，是架构问题——第一版代码把三个协议长进了主程序身体里，本章讲怎么把它们请出去：虚函数划接口，工厂做注册，dlopen 管加载。顺便把 vtable 掀开给你看——面试里 80% 的人背过「虚函数表」这个词，只有 20% 说得清它长什么样。

## 一、事故现场：加一个协议，全公司陪跑

第一版面对新协议的写法，大概是这个样子的：

```cpp
// collector.cpp —— 核心层，包含了所有协议的头文件
#include "modbus_driver.h"
#include "opcua_driver.h"      // 拖进来整套 OPC UA SDK 头
#include "acme_driver.h"       // 客户 C 的私有协议

Frame Collector::read_channel(int ch) {
    switch (cfg_.protocol) {
        case Protocol::MODBUS:  return modbus_.read(ch);
        case Protocol::OPCUA:   return opcua_.read(ch);
        case Protocol::ACME:    return acme_.read(ch);
    }
    throw std::runtime_error("unknown protocol");
}
```

能跑，但账单随后就到。给客户 C 上私有协议的那一周：核心层 `collector.cpp` 动了、CMake 动了、配置结构动了，**全量重编 12 分钟**，200 个存量回归用例全部重跑——为一个跟存量毫无关系的新协议。更烦的是头文件污染：OPC UA SDK 的头文件和某个第三方库的宏定义打架，编一次修一次。而客户 C 的协议实现有个 bug，修复它意味着**所有客户的网关都要重新发版**——只因为那坨代码被编译进了主程序。

最要命的是第 05 章预告的那个事实：协议解析是产线上最容易出 bug 的代码。最容易出 bug 的代码，被我们放在了最难独立发布的组件里。

## 二、排查过程：把「架构病」当「性能病」来诊断

这章没有崩溃可查，排查的对象是依赖关系本身。三步：

第一步，量化痛点。统计「新增一种协议」的完整成本：动 7 个文件、编译 12 分钟、全量回归 200 用例、所有在网设备重发版。数字摆出来，结论就不需要争论了。

第二步，画依赖方向图。现状是核心层 include 了每一个协议实现——**依赖箭头全部指向核心**。可正确方向应该反过来：核心只认识一张「驱动接口」契约，每个协议实现自己贴上来。依赖倒置原则在工业代码里的具体形态，就是一张接口头文件。

第三步，定目标，用一句话锁死验收标准：**新增协议 = 放一个 .so 进 drivers/ 目录 + 配置里写一行协议名，主程序零改动、零重编**。这句验收标准后来写进了网关的 README，比任何设计文档都管用。

## 三、底层原理：vtable 长什么样，虚析构为什么是铁律

### 虚调用的机械成本

编译器给每个含虚函数的类生成一张虚函数表（vtable）——本质是只读数据段里的函数指针数组；每个对象里塞一个隐藏指针（vptr）指向自己类的表。调用 `driver->read(ch)` 时，机器实际干的事是两级间接寻址：

```text
1. 从对象头部取出 vptr            →  一次内存访问
2. vtable[槽位] 取出函数地址      →  再一次内存访问（可能 cache miss）
3. 间接 call 到 read()            →  无法内联
```

所以虚调用的真实代价是：两条 load 指令 + 一条间接跳转 + **丧失内联机会**，典型 1~2ns，若有 cache miss 则放大。要不要怕它？第五节给实测数字，先剧透结论：架构层每个采集周期调十几次，可忽略；若在最内层循环按采样点虚调用（每秒 10 万次），才需要 ch09 的模板手段。

### 虚析构：delete 基类指针时的半截资源

铁律场景：接口指针管理实现对象（`Driver* d = new AcmeDriver();`），销毁时 `delete d`。若基类析构不是虚的，**delete 一个基类指针只调基类析构，派生类部分不析构**——这是标准明文规定的未定义行为，实际表现就是「删了上半截」：`AcmeDriver` 里的 socket、缓冲区原地泄漏。这正是 ch02 那场 fd 泄漏的另一种打开方式，而且更隐蔽——ASan 报泄漏的栈指向 `delete d` 那一行，你却看不出哪里没删。

所以接口类的第一行永远是：

```cpp
class Driver {
public:
    virtual ~Driver() = default;              // 铁律：接口析构必须虚
    virtual Frame read(int channel) = 0;      // 纯虚 = 契约
    virtual std::string_view name() const = 0;
protected:
    Driver() = default;
};
```

顺带一个面试加分区：**构造/析构期间调用虚函数不会派发到派生类**——构造基类时 vptr 指的还是基类的表，此时虚调用只落在本层实现。接口类的构造函数保持 protected + default，就是从写法上断掉这个念想。

### dlopen 与 C ABI 边界

动态库加载机制三件套：`dlopen` 把 .so 映射进进程地址空间（顺便执行它的静态初始化），`dlsym` 按符号名取地址，`dlclose` 逆操作。插件自注册的经典套路就是利用第一点——.so 里放一个全局对象，构造函数把自己的工厂函数注册进主程序的注册表。

但 .so 的边界上有一条红线：**C++ 异常和 std::string 等标准库对象不许穿越**。两个 .so 可能是不同编译器版本编的，异常的展开机制和 std::string 的内存布局没有跨边界保证（ABI 兼容问题）。所以导出函数必须是 C 风格：`extern "C"`、裸指针进出、错误用返回值——这既是本章的插件约定，也是 ch10「异常穿越动态库边界崩溃」那一章要深挖的主题。

## 四、正确姿势：一张接口 + 自注册插件

协议侧（每个 .so）导出两个 C 函数，内部完成接口实现：

```cpp
// drivers/acme_driver.cpp —— 客户 C 私有协议
#include "driver.h"
#include <dlfcn.h>

namespace {
class AcmeDriver final : public Driver {
public:
    explicit AcmeDriver(const DriverConfig& cfg) {
        conn_ = std::make_unique<TcpConn>(cfg.host, cfg.port);
    }
    ~AcmeDriver() override = default;             // override 让编译器盯着签名
    Frame read(int channel) override {
        /* 私有协议帧解析，ch05 的主角 */
    }
    std::string_view name() const override { return "acme"; }
private:
    std::unique_ptr<TcpConn> conn_;               // ch02 的成果：资源自动归位
};
}  // namespace

extern "C" Driver* create_driver(const DriverConfig* cfg) {
    return new AcmeDriver(*cfg);                  // C ABI 边界：裸指针进出
}
extern "C" void destroy_driver(Driver* d) { delete d; }
```

主程序侧，dlopen + unique_ptr 接管（注意自定义删除器接的是 `destroy_driver` 而非 delete——跨边界资源谁导出谁回收）：

```cpp
using CreateFn = Driver* (*)(const DriverConfig*);
using DestroyFn = void (*)(Driver*);

DriverHandle load_driver(const std::string& proto, const DriverConfig& cfg) {
    void* h = dlopen(("drivers/" + proto + ".so").c_str(), RTLD_NOW | RTLD_LOCAL);
    if (!h) throw std::runtime_error(dlerror());
    auto create = reinterpret_cast<CreateFn>(dlsym(h, "create_driver"));
    auto destroy = reinterpret_cast<DestroyFn>(dlsym(h, "destroy_driver"));
    if (!create || !destroy) throw std::runtime_error("bad plugin: missing symbols");
    return DriverHandle{create(&cfg), [destroy, h](Driver* d) {
        destroy(d);                               // 插件自己的 destroy
        dlclose(h);
    }};
}
// using DriverHandle = std::unique_ptr<Driver, ...>;  接口操作全程虚调用
```

验收标准兑现：客户 C 的协议从接需求到上线，主程序一行没动、一次没编，drivers/ 目录多了一个 .so。同场加映两条工程守则：**接口一旦发布，只加不改**（改已有虚函数的签名或顺序 = 全部插件作废）；给接口留个 `version()` 虚函数，主程序加载时核对协议版本，防「老插件配新主程序」的静默错位。

## 六、面试怎么答

**Q1：讲讲虚函数的实现机制。**
框架：每个多态类一张 vtable（编译期生成，放只读段），每个对象一个 vptr（构造时写入）；虚调用 = vptr 取表 + 表取函数指针 + 间接跳转。加分项主动讲三个：构造期间虚调用不派发到派生类；多重继承会有多个 vptr；间接跳转导致无法内联，所以极热路径用 CRTP/模板替代（预告 ch09）。

**Q2：为什么基类析构函数必须是虚函数？**
机制：delete 基类指针时，非虚析构只调基类析构，派生部分不销毁，属未定义行为，实际后果是资源泄漏——我可以现场讲我们网关的 socket 半截泄漏事故（delete Driver* 只跑了 Driver 析构，AcmeDriver 里的 TcpConn 没人管）。收尾补一句：凡是「用基类指针管理派生对象」的场景，虚析构不是建议，是编译器没法替你兜底的铁律。

**Q3：C++ 怎么实现插件热加载？有哪些坑？**
三件套 dlopen/dlsym/dlclose + C ABI 导出函数 + 接口纯虚类。坑按条数背：异常和 STL 对象不许穿 ABI 边界；谁分配谁释放（跨边界 delete 是 UB 高危区）；插件静态对象在 dlopen 时初始化、dlclose 时析构，顺序和生命周期要设计；RTLD_LOCAL 防符号污染。

**Q4：接口发布后怎么保持二进制兼容？**
只加不改：新增虚函数只能追加在末尾（vtable 槽位按声明序），不删不改不动顺序；改行为用新函数名；跨大版本用版本号协商（接口里放 version()）。懂行的话再提 pimpl——把易变实现藏进 impl 指针后面，导出层只暴露一个不透明的类。

## 七、落地清单

- 接口类：纯虚函数 + `virtual ~T() = default` + protected 构造，三件套一个不能少
- 所有 override 都写 override 关键字，签名错误让编译器抓住
- .so 边界：extern "C" 导出、裸指针进出、成对的 create/destroy、谁导出谁回收
- 主程序用 unique_ptr + 自定义删除器接管插件对象，dlclose 与 destroy 绑定同一条路
- 接口只加不改；加 version() 虚函数做加载时核对
- 插件目录与主程序隔离，发版物清单里 .so 与主程序版本号分开管理
- 架构层放心用虚调用；每采样点级别的热路径留给 ch09 的模板

三种协议从此各自安好。但协议 .so 一多，暴露在外的就是协议解析本身——下一章的原油没拧干净：TCP 粘包拆包，一字节偏移让温控指令写进了涂布机，产线现场的真实事故。
